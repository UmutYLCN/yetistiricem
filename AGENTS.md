# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Checks: `npm run build`, `npm run lint`, `npm test` (strict type-check of `tests/` via `tsconfig.test.json`, then `node --test` with type stripping; no test framework dependency). Modules that tests or `server/` import must use explicit `.ts` import paths down their whole chain.
- Dates are local `YYYY-MM-DD` keys; use `src/utils/date.ts`. Never `new Date('YYYY-MM-DD')` or `toISOString().split('T')[0]`: both shift the day outside UTC.
- The schedule depends on completion only through early finishes: a task ticked before its planned day moves to its tick day and later tasks move up (replayed from `yt_completed_on`, ticks from `aheadSince` on); otherwise ticking only decorates `item.completed`. Shifts are stored events (with the postpone `reason` asked in `PostponeReasonDialog`; `origin: 'branch-added'` ones are not postponements), and `postponeCount` is derived from them, never stored. Tick days live in `yt_completed_on`; older ticks have none, so progress insights (`src/lib/insights.ts`) never guess one. See `docs/planner-engine.md` for the engine and UI contract.
- Data model: a `StudyCamp` owns its branches (`SubjectPlaylist`; `subject` = branch name), its tempo (`CampSchedule`, auto or manual `weekPlan`) and its shift events, and is always scheduled alone with `buildCampSchedule`. Plan screens show the one camp, or from two camps on always `buildAllCampsPlan` (`src/lib/allCamps.ts`), which merges the separately built plans by date; there is no camp switcher or filter (`yt_camp_scope` is retired). A paused camp (`pausedAt`, set in Kamplar) keeps its data but stays off the plan screens and MCP plan (`runningCamps`/`campsWithPlans`); resuming (`withResumed`) carries its open past tasks to today with an `origin: 'resumed'` event, not a postponement. Each shift event goes to the camp owning its tasks. Management, dialogs and `yt_active_camp` always use a concrete camp. Tempo is per camp only, edited with "Tempoyu düzenle" in Kamplar (never in Ayarlar; plan screens carry no camp/tempo bar). "Branş ekle" adds to the camp it opened for (`addBranches`), never creates one. Data updates go through `src/lib/plannerOps.ts`; wizard rules in `src/lib/campDraft.ts`. Product notes and V1 boundaries: `docs/camp-creation-wizard-notes.md`.
- UI code reaches the engine, storage and date helpers only through `src/lib/engine.ts`. Loading, legacy migration and backups live in `src/lib/persistence.ts`: `yt_camps` is authoritative; `yt_camps_migrated` prevents old flat keys from recreating deleted camps if it goes missing. The older keys are read-only migration input, never written. Cloud sync (`cloudState.ts`, `cloudSync.ts`, `useCloudSync.ts`) uploads only a copy owned by the signed-in account; ownerless local data is backed up, never silently merged. Keep the existing `yt_*` keys, and never drop stored data silently (copy it aside and show a notice).
- Data truth: never invent videos, links, durations or channel names. Video data comes from the user (topics typed with a duration, link-less) or from the server-side YouTube endpoints (`server/`: playlist and videos, YouTube Data API v3; contract in `src/utils/youtubePlaylist.ts`, setup in README). The daily playlist check (`src/lib/playlistSync.ts`, at most one a day for the quota) only offers new playlist videos in the bell; they join a branch on the student's click. Demo templates (`src/data/demoTemplates.ts`) are labelled and link-free; old fabricated camps are detected in `src/lib/camps.ts`.
- `YOUTUBE_API_KEY` is server-only: never give it a `VITE_` prefix, read it in `src/`, or echo it or upstream error text in endpoint responses. `tests/keySecrecy.test.ts` builds the bundle to check. The endpoints accept only validated ids (one playlist id, or up to 50 video ids), never a URL; a new route also needs `public/_routes.json` and a `functions/` file for Pages.
- MCP (`docs/mcp.md`): `POST /mcp` is a hand-rolled stateless Streamable HTTP server (`server/mcp/`, no SDK). Every request needs an OAuth token from Supabase Auth's OAuth server (only tokens with a `client_id` claim; the student approves at `/oauth/consent`); the server holds no service key and uses that token, so RLS applies. Tools read the plan and progress (`myPlan.ts`, the app's own engine and insights); `send_camp` validates JSON against `campFormat.ts` and re-reads every YouTube id, then saves only a private `mcp_camp_drafts` proposal. `add_kesfet_camp` also stages a proposal. The student sees every item at `/app?draft=<id>` and alone adds the camp; never let an MCP call write it directly. `server/` imports `src/` modules, so `tsconfig.node.json` type-checks that chain too (no DOM there: keep `window` out of it).
- Keşfet (`docs/kesfet.md`): published camps live in Supabase (`src/lib/catalogApi.ts`, loaded on demand; schema and RLS in `supabase/migrations/`). `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` are public by design; never a service-role key in `src/`. Catalog rows come from other people: re-check them (`src/lib/catalog.ts`, the share-link checks) before showing or importing.
- Modals go through `src/components/ui/Dialog.tsx` (native `<dialog>`: focus trap, Escape, focus return; `placement="full"` for the focus player) and confirmations through `useConfirm`. An open `<dialog>` sits in the top layer, so anything drawn over it (e.g. confetti) needs its own canvas inside the dialog.
- Pages on one bundle: `/` landing (`src/components/landing/`), `/app` planner, `/docs[/<page>]` docs (`src/components/docs/`, pages in `content.tsx`; how-to text lives there, not in the app), `/oauth/consent` AI connection approval; `src/Root.tsx` picks by path, `src/lib/routes.ts` has the paths, `/app?demo` and `/app?import=<payload>` (camp share links, untrusted input; format in `docs/camp-share-link.md`). Both flags leave the address bar in `src/main.tsx` before the app renders. `/app` needs an account (`AuthGate`, `docs/kesfet.md`) except in the demo; the planner mounts at most once per page load, so sign-out and an ended session reload the page instead of unmounting it. Links between them stay full page loads, never client-side routing: `loadPlannerOnce` caches storage per page load, so a remounted planner would show and save stale data. Never add `public/404.html`: Cloudflare Pages then drops the SPA fallback that serves `/app`.
- Localization: `src/lib/language.ts` persists `yt_language` (`tr`, `en`, `es`, `fr`); `src/i18n/` holds the phrase catalogs and `src/lib/messages.ts` resolves them through `msg()`. The selector lives below Appearance in `SettingsDialog`. Add translations when adding visible copy, localize dates and numbers through `src/lib/format.ts`, and leave user-entered names and content untouched.
- Brand: the product is **Yetişir**, with a lowercase **yetişir.** wordmark (“Panik yok, yetişir.”; `BrandMark` + `Wordmark` in `src/components/ui/BrandMark.tsx`), in a calm, guilt-free tone (the reschedule action is “Ritmi güncelle”). Technical ids keep the old name on purpose: the `yetistiricem.pages.dev` address, `yt_*` keys, the share document's `app: 'yetistiricem'`, the MCP server name, the repo. Changing them breaks stored data and links.
- Light and dark themes. Colors come from the role tokens in `src/index.css` (`paper` page, `card`/`sunk` surfaces, `ink*` text, `on-fill` on bright fills), never raw hex in components; a token's light value lives next to its dark one in the same file (`@media (prefers-color-scheme: light)` and `[data-theme="light"]`), so a new color needs both, and a new decorative literal (a glow, a translucent border) should be `color-mix(in srgb, var(--color-ink) X%, transparent)`, not a literal white, so it flips with the theme. `src/lib/theme.ts` (`yt_theme`: `light`/`dark`/`system`) applies the override as `data-theme` on `<html>`; `index.html` carries a blocking script mirroring it so an explicit choice paints with no flash. `ThemeIconToggle`/`ThemeSegmented` (`src/components/ui/ThemeToggle.tsx`) are the landing header's and the Ayarlar window's controls (`SettingsDialog`, the gear next to the sidebar profile; app options go there, the account stays on the profile page). The branch palette (`src/lib/subjects.ts`) stores a `colorTag` key per camp, never a color; its `solid`/`soft` are `var(--palette-<key>-solid/soft)` references, each with a light and dark value in `src/index.css`, so re-theming needs no data migration. Landing styles live in `src/components/landing/landing.css`: flat surfaces, subtle borders, abstract UI illustrations. Product previews reuse app components and demo data (`buildLandingPreview`), rendered `inert`; the walkthrough only changes local presentation state. Placeholder testimonials must stay explicitly labelled as examples.
